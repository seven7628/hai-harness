## 0. 评审结论摘要

**总体判断**：V2 在**协议分层、引用类型、判定四层、预览注入时机**上是对的，且把"现状五个硬伤"
定位准确。但它**只是元设计的一个子集**——元设计里三条最重的机制（**自检闭环、两条修改路径、
导出规范**）在 V2 中完全缺失；另有 **3 处与代码现实/元设计直接冲突**，若不改，落地时会返工。

### Top 6 必须修的问题

| # | 问题 | 严重度 | 一句话影响 |
|---|---|---|---|
| 1 | **自检闭环（Verifier）完全缺失** | 🔴 P0 | 页面打开了但白屏/报错时无人自愈，用户看到"成功"的坏页面 |
| 2 | **两条修改路径只做了一条** | 🔴 P0 | 改个颜色也要过 LLM，成本与延迟差一个数量级 |
| 3 | **`old_str/new_str` 字符串替换与 React 冲突** | 🔴 P0 | 元设计明确 React 必须 AST 改写；字符串替换会破坏手改与格式 |
| 4 | **产物区与版本库的目录语义混为一谈** | 🔴 P0 | 元设计是 `artifacts/<id>/`（可见、路径即意图），V2 写成 `.artifacts/`（隐藏） |
| 5 | **传输选型一律本地 HTTP，丢了独立 origin** | 🟠 P1 | Electron 内嵌本可用 `artifact://` 隔离；HTTP 需要额外做 CSP/Origin/Host 三件套 |
| 6 | **子 agent 产物继承未列** | 🟠 P1 | 历史 §21.16 明确要求，**代码确认未实现**，多 agent 场景会漏产物 |

## 5. 需要拍板的三个架构分歧

| # | 分歧 | 选项 A | 选项 B | 评审建议 |
|---|---|---|---|---|
| D1 | **存储** | 文件目录 + 内容寻址（V2 现方案） | SQLite + 内容哈希（元设计） | **A**。仓库无 SQLite 依赖，引入驱动+迁移+事务成本高；产物量级（<1GB）文件足够。代价：并发写加锁、GC 自写。**建议 A，并记录偏离理由** |
| D2 | **传输** | 一律本地 HTTP（V2） | Electron 内嵌用 `artifact://`，浏览器/移动用 HTTP（元设计倾向） | **B 双通道**。自定义协议自带独立 origin（天然隔离、无端口、无 Host 校验问题）；HTTP 留给移动/浏览器。代价：两套 URL 生成逻辑 |
| D3 | **编辑落盘** | `old_str/new_str` 字符串替换（V2） | 纯 HTML 用替换；React/TSX 用 **AST 改写**（Babel/ts-morph） | **B 分类型**。元设计明确 React 不能字符串替换。V2 需按 `Entry` 扩展名分派 |

## 6. V2 修订清单（可直接执行的补丁）

### 6.1 必改（P0）

1. **新增 §4.4「自检闭环（Verifier）」**：时序（Version Store → 加载 → 收集错误 → 双视口截图 →
   `verify.report` 回灌 Agent → 最多 2 轮 → `artifact.ready`）+ 检查项（console.error/pageerror/
   失败请求/横向溢出/空白页/对比度）+ 失败降级（不静默输出空文件）
2. **新增 §6.7「两条修改路径」**：确定性 patch（颜色/字号/文案，不经 LLM，op 列表如下）
   vs Agent 路径（布局/风格/重构）；两者共用 `artifact_edit` 的 `base_version` 校验
3. **改写 §7.4「编辑落盘」**：按入口类型分派——`.html` 用 `old_str` 唯一匹配替换；
   `.tsx/.jsx` 必须 AST 改写；`instances > 1` 与 `dynamic: true` 语义按元设计写清
4. **修正 §5.3 目录语义**：区分 `artifacts/<id>/`（产物区，源码，可见）
   与 `.artifacts/`（版本库，快照，隐藏）；给出一句话对照，避免实现时合并
5. **新增 §7.2 M9**：子 agent 产物声明表继承（`subagent/*.go` + `agent_loop.go` 收尾合并）

### 6.2 应改（P1）

6. **§7.2 补 C1/C2/C3/C4 四条修正**（路径归一 posix、`artifact.ready` URL 重算、
   快照补 hash、绝对路径资源子域方案）
7. **新增「导出规范」节**：矩阵 + 约束（warnings、文件名、50MB、剥离注入属性）
8. **补「画布与 Design type」节**：`boards/<id>.html`、`^[a-z0-9-]{1,32}$`、
   `data-nid ^n_[0-9a-z]{6}$`、tokens lint、stamp 版本 `kind:"stamp"`（可从 P8 提前到"设计约束先行"）
9. **补「坐标换算与边界降级」**：缩放/滚动/sticky/transform/虚拟列表/伪元素/主题断点
10. **补「Composer chip 复用」**与「公共能力抽取」（历史 §23.4/§23.7）
11. **补「打开策略」**：autoOpen 三档、一次一个、CI 跳过、入口变化不跳转
12. **统一指标术语**为声明召回率 / 误报率 / 漏检率 / 一次通过率 / 选区解析成功率 / 回滚率
13. **补 provenance**：生成脚本记来源，支持"重新生成"

## 8. 结论与建议动作

1. **V2 的骨架可用**，不必推倒；需要的是**补三章 + 修两处冲突**：
   - 补：自检闭环、两条修改路径、导出规范
   - 修：目录语义（产物区 vs 版本库）、编辑落盘（按类型分派 AST/字符串）
2. **三个分歧（D1 存储 / D2 传输 / D3 编辑）建议先拍板再动手**，否则 P0/P1 会返工。
3. **元设计最后那 4 条"对初版代码的修正"是最廉价的收益**——都是几行代码的事，
   但不做会在联调阶段被反复咬住，建议直接写进 V2 的 §7.2 M 列表并配测试。
4. 建议 V2 升为 **v2.1** 后进入评审冻结，再按 §14 阶段推进；P0 阶段先补 Verifier，
   因为它影响"用户到底看到成功还是失败"这个最外层体验。
